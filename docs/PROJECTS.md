# Projects — identity, layout and the commands around them

M2.2's server half (migration 012, the repository, the store and the five routes) and this
milestone's operator surface. Read this before changing anything that names a project, stores a
secret for one, or puts a path on disk.

## Identity: the uuid is the project, the slug is the label

| | |
| --- | --- |
| **`uuid`** | RFC 4122, generated by `crypto.randomUUID()`, canonical **lowercase**. The identity: every route address, every directory name, every AAD component, every foreign key. Never changes. |
| **`slug`** | 2–40 characters, `[a-z0-9]` with hyphens in the middle, NFC-normalised and lowercased. The **label**: shown in the UI, used for lookup on the command line, mutable at any time. |

Two consequences, both load-bearing:

- **A rename is a database write and nothing else.** It does not move a folder, does not
  invalidate an encryption AAD, and does not change a URL. The panel's project screen is
  addressed by `/projects/<uuid>` only; the slug appears in the heading and in no path.
- **Normalisation is duplicated on purpose only where it cannot accept anything.** The client
  compares a returned slug against `requested.normalize('NFC').toLowerCase()` to choose between
  "renamed to X" and "your name was taken, so it is X" — copy, not validation. The server's
  `normalizeSlug()` is the only thing that decides whether a slug is acceptable, and a
  `slug_normalized` generated column carries the uniqueness constraint so two inputs that fold
  together cannot both exist even if a future path forgets to normalise first.

A collision is resolved with a `-2`, `-3`, … suffix, truncating the stem when the suffix would
push past 40 characters. The create response says so through `renamed: true`; the PATCH response
uses the same word for a different question (did the stored label actually move), which is why
the screen compares the result against what was requested rather than trusting the flag.

## On-disk layout

```
<data>/
├── projects/
│   └── <uuid>/
│       ├── workspace/       # the checkout the agent runs in
│       ├── claude-home/     # CLAUDE_CONFIG_DIR — a sibling, never a descendant
│       └── project.json     # uuid, slug, createdAt, schemaVersion, isolatedSettings
├── .project-stage-<uuid>/   # creation staging, a sibling of projects/ (see below)
└── .project-orphan-<uuid>/  # quarantine: promoted tree whose DB commit failed
```

- Directories are `0700`, files `0600`.
- `claude-home` is a **sibling** of `workspace` rather than inside it: `CLAUDE_CONFIG_DIR` set
  inside the workspace would be part of the checkout (and therefore importable, committable
  content, and a settings file that overrides the panel's).
- `project.json` is written atomically (temp file in the same directory, then `rename`) and has
  a **key denylist**: `api_key`, `hook_token` and the other credential-shaped names are refused
  by the writer itself, so a credential cannot be persisted into it by accident.
- Staging lives **outside** `projects/` for two reasons: the boot sweep walks a prefix beside
  `projects/`, so a staging directory inside it would be mistaken for a project; and `rename(2)`
  stays atomic only within one filesystem, which a shared parent guarantees.

### Creation order and its failure modes

1. **Disk guard** (`checkDisk`) — refuses when used space has reached the watchdog's disk
   threshold. The refusal is `DiskGuardRefusedError`, generic by design: no path, no byte
   count, no base path. The route turns it into `507 insufficient_storage`.
2. **Slug validated**, uuid chosen.
3. **Staging tree** built. Fails → staging removed; nothing on disk, nothing in the database.
4. **`rename(2)` promotion** into `projects/<uuid>`. Fails → staging removed; nothing in the
   database.
5. **One database transaction**: `INSERT`, then the `project.created` audit append, then
   `COMMIT`. The filesystem half is deliberately outside the transaction — recursive syscalls
   under SQLite's write lock would block every other writer in the panel. If the transaction (or
   the audit append) fails, the already-promoted tree is **quarantined** to
   `.project-orphan-<uuid>` rather than renamed back: a rename-back can itself fail, while
   moving the tree aside always leaves `projects/` free of rowless directories.

### Deletion order and its crash residual

1. **One database transaction**: `project:<uuid>` secrets, then the row, then the
   `project.deleted` audit append. Secrets before the row so an aborted attempt leaves a row
   with no credentials rather than a credential with no row.
2. **`rmSync` of the project directory** — workspace, claude-home, project.json and the
   directory itself.

A crash between the two leaves a directory with no row: invisible in the UI, ignored by the
boot sweep (which only ever walks the staging prefix), and found deterministically by
`diagnoseProjectDirs()`.

## The rowless-directory diagnostic

`ProjectStoreService.diagnoseProjectDirs()` is **read-only**: it lists immediate children of
`projects/`, classifies each as a database-backed project, a canonical-UUID directory with no
row (`rowless`), or ignored (not a uuid; a symlink is classified, never followed). It never
deletes, and `bootSweep()` is not allowed to grow into a collector of rowless directories —
automatic deletion of a directory the database cannot account for is how a crash between the
two deletion steps would silently destroy the only copy of a workspace. Cleanup is an operator
decision, made with `project:path` and `ls` in hand.

## `npm run project:path -- <slug>`

The command-line half of the identity rule: **slug → uuid → workspace path**, resolved through
the repository and never by scanning folders.

```
$ npm run project:path -- my-project
/data/projects/3f6a1d20-9b41-4c7e-8d2a-5e1f0b7c9a44/workspace
```

- Exactly one argument. It is normalised and validated with the same canonical rules as the
  API, then looked up by `slug_normalized`.
- Success: the workspace **absolute path**, alone on stdout, with a trailing newline and no
  label — so `$(…)` works.
- Everything else (no argument, malformed slug, unknown slug, uuid that fails
  `CANONICAL_UUID`, unusable environment): one line on stderr,
  `project:path: could not resolve that project`, exit `1`, stdout empty. No candidate slugs, no
  path, no database contents, no base path.
- Read-only by construction: the connection opens `readonly: true, fileMustExist: true`, no
  directory is created, no symlink is followed (the uuid is validated before it is joined), and
  no credential is printed.

## Secret AAD forms

Two forms, exact and **not interchangeable** — each is what its own producer writes, and the
reader picks the scheme from the stored prefix:

| Purpose | AAD |
| --- | --- |
| a project's future `api_key` | `projects:<uuid>:api_key` |
| a project's future `hook_token` | `secrets:project:<uuid>:hook_token` |
| the project's secret **scope** (a `secrets` row) | `project:<uuid>` |

The uuid component is validated as canonical before it is joined, so an untrusted component
containing `:` (or `/`, `.`, `..`, NUL, or nothing at all) can never reach an AAD.

## The four audit events

`project.created`, `project.updated`, `project.deleted`, `project.create_refused`.

- **`project.updated`, never `project.renamed`.** A slug change, an `isolatedSettings` change
  and a change to both are all one event, with `previousSlug`, `isolatedSettings` and whether
  the label actually moved in the metadata. A second event name would be a second thing for the
  operator to learn about a single write.
- **`project.create_refused`** is the disk guard's row: `reason: 'disk_guard'`, name only, never
  a path or a threshold.
- **Only `project.deleted` notifies.** The other three have an explicit `null` rule in
  `services/notification-rules.ts`, with the reason in a comment — a create or a rename is
  something the operator just did and is looking at.
- Deletion's success row is appended **inside the same transaction** as the row and the secrets
  it describes, so a deletion and its audit row are one atomic unit.

## The disabled-tab map

The project screen is addressed by uuid and shows a summary today. Everything else is a
**disabled tab** carrying the milestone that will build it, so the shape of the screen says what
is coming and where:

| Tab | Milestone |
| --- | --- |
| Summary | built here |
| Files | M2.3 |
| Portability | M2.4 |
| Telegram | M2.5 |
| Settings and credentials | M2.6 |
| Import | M2.8 |
| Terminal | M3 |

Each unbuilt tab is `aria-disabled="true"` — never the `disabled` attribute, which would take it
out of the tab order and hide it from a keyboard user — and all six share one visually hidden
`aria-describedby` naming the reason.
